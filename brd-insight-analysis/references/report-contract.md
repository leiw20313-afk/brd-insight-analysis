# 报告契约

网页读者是业务人员。全文用简洁、专业的中文，沿用一致且准确的业务术语；必要的专业词首次出现时用业务语言简要解释。用稳定编号和分层标题连接概览、场景、问题与决定。**不要求同一场景只完整呈现一次**：结论可摘要主线，用户故事概览用于快速浏览，场景链用于逐步核对，确认事项用于表达待决定内容；按各自阅读目的适度呈现，避免机械重复。报告不按部门拆分，不展示材料来源或内部分析过程。

## 阶段一：按五个问题阅读

### 1. 一页纸结论：我们要解决什么？

用短句或小型定义列表，不铺陈背景。可用两列表格让业务快速对照：

| 栏目 | 写法 |
|---|---|
| 用户与任务 | 谁在什么时点最需要取得什么结果；核心故事可写已明确的购买或采用条件。 |
| 现在怎么做 | 现行做法、参与角色及必要交接，不写拟上线能力。 |
| 哪里受阻 | 哪一步缺什么，会影响哪一个结果；不笼统说“体验不好”。 |
| 流程一句话 | 标清“目标流程”或“现行流程”。用“触发 → 关键判断/动作 → 结果”串起主线，不堆例外。 |
| 本期范围与进度 | 含什么、不含什么；标明最新确认状态和仍待决定的事项。 |

前三项中的事实缺失时保留相应栏目，写“当前做法未说明”“阻点尚未明确”等，不猜原因；目标流程尚未定时也要标明。只有影响决定的缺口才进入确认清单。

### 2. 用户故事概览：业务价值落到哪些用户任务？

先用目标-故事覆盖表展示业务提出的目标/价值、用户应得到的结果、对应已确认故事，以及尚未覆盖时的候选故事。候选明确标为“待业务确认”，不得与已确认故事混作本期承诺。输入材料中每项业务目标/价值都必须有一行去向：已确认故事、待业务确认候选，或业务明确说明不属于本期用户场景；不得留空，也不得为了填满而虚构用户任务。

| 业务目标/价值 | 用户应得到的结果 | 已确认用户故事 | 未覆盖的候选故事/状态 |
|---|---|---|---|
| [目标/价值] | [用户结果] | [故事编号或暂无] | [候选故事及编号/待业务确认，或暂无] |

随后列故事概览：`序号｜角色｜用户任务｜期望结果`。同角色相邻；已确认故事与候选清楚区分。序号可链接到故事链。概览与场景链可适度重提角色、任务或结果以便独立阅读；概览保持短小，场景链写完整步骤。

逐项目标/价值执行覆盖检查：推导其承诺的用户结果，核对是否有目标用户、触发情境、任务和场景支撑；再检查达成该结果必需的角色交接、关键分支、阻断条件和失败恢复。发现缺口时，提出具体候选故事/场景并说明关联目标、未覆盖的用户结果及若不纳入的风险。逐项目标完成映射后，覆盖表不得遗留空白；若需业务决定候选是否纳入，保留为待确认项。候选是待业务判断的推导，不是已发生的用户事实；不为凑数列无关异常，也不宣称穷尽所有现实情境。

### 3. 场景故事链：还原是否符合原意？

所有场景按实际业务发生顺序排列，并以业务目标和价值为覆盖基准；不拆成“主流程 / 次要流程 / 异常流程”模块。每个场景标题带一个流程类型标签，如“主流程”“分支流程”“异常流程”；分支与异常插入其在业务链中出现的位置。没有已知分支不编造；依据目标/价值推导的候选必须清楚标“待业务确认”，不能混入已知流程。场景标题即使收起也能看清**流程类型、关联故事、场景名**；阶段一默认展开首个主流程，其余可收起。

| 详情字段 | 足以确认原意的写法 |
|---|---|
| 角色、触发与目标 | 谁在什么条件下进入，要得到什么结果。若角色发生交接，写清由谁接手。 |
| 场景步骤 | 按实际顺序写“谁做什么 → 下一步如何判断”；现行、拟议不能混写。 |
| 业务规则与页面功能 | 根据场景判断用户是否需要页面来录入、选择、查看、编辑或提交信息。需要时，在该场景里写明所需功能及业务规则，并确认会影响任务的细节。 |
| 范围边界 | 哪些对象、阶段、条件适用；到哪一步结束、哪些不做。 |
| 验收标准 | 给定具体情境，能观察到什么结果才算满足；能区分通过/不通过，不杜撰阈值。 |

缺少会改变承诺的内容，在对应字段写红色“未确认”标记及问题编号；把问题全文直接放在本场景的待确认折叠区中，不要求读者跳转查看。折叠区默认收起，标题显示未确认数量；展开后列出该场景全部未确认问题、确认原因、确认标准及已有答复。不要用猜测补齐。对每个涉及页面功能的未确认规则，具体问业务：自由文案需确认字数上限及超限处理；枚举控件需确认可选值和最多可选数量；其他字段按场景需要确认必填性、校验条件及反馈结果。不得替业务编造限制值。已确认项不重问。修改若改变用户、步骤、规则、页面行为、边界或验收，先改场景再请业务核对改动点。

### 4. 风险遗漏场景：目标和价值是否有未覆盖的用户情境？

独立于故事链中的已承诺流程。候选可关联已明确故事，也可直接关联尚未由故事承接的业务目标/价值。先检查目标/价值对应的用户结果是否有场景支撑，再补充有明确目标锚点、若不考虑会产生具体影响的情境。候选不声称穷尽所有现实场景。每项先在折叠详情之外醒目标出**若不考虑的风险**，随后以可展开的具体场景展示角色/触发、步骤、业务规则、范围边界和验收标准；标题带“风险遗漏”及主流程/分支流程/异常流程等类型标签。每项保留独立编号，并链接到关联故事和对应确认项。未知字段写待定；讨论中的处理或验收标“拟议”，不是现有承诺。

- **若不考虑的风险：**说明新条件、哪项用户结果未覆盖或已知场景的哪一步可能断开，以及用户/业务会受到什么具体影响。无故事或业务目标/价值锚点、且无具体风险的不列；没有合格项时简要注明。
- **范围决定：**请业务决定“纳入本期 / 暂不考虑”，链接至对应确认项。纳入后补齐规则和验收，并在原业务顺序中增加对应场景；遗漏编号保留作可点击映射。暂不考虑即本期不承诺，在边界中说明。

示意：

```html
<div id="risk-impact-c1" class="finding"><strong>若不考虑：</strong>若车辆接口已改装但仍沿用原厂适配信息，车主可能买到无法安装的雨刷。</div>
<details id="risk-c1" data-scene>
  <summary><span class="risk-tag">风险遗漏</span> <span class="flow-tag flow-exception">异常流程</span> · 关联 <a href="#story-1">故事 1</a> · C1 改装接口</summary>
  <h4>业务规则</h4><p id="rule-r2">尚待业务决定是否转人工核对。</p>
  <p>确认范围：<a href="#q4">Q4</a>。</p>
</details>
```

风险说明在折叠场景前始终可见；点击标题或相关编号可打开并定位到具体内容。

### 5. 待确认事项与确认记录：这次需要回答什么？

以所属场景为入口查看待确认问题全文；本节作为集中确认记录，按场景顺序列出事项名称（含编号和状态标签）、实际答复和历史答复，名称链接可回到所属场景。**状态只有“未确认”和“已确认”**：任一要求尚未明确、答复不完整或规则细节仍待定，当前状态均为“未确认”；只有全部确认标准满足且得到明确答复才为“已确认”。不存在“部分确认”“需修改”“待复核”等中间状态；已回答的部分可记入答复，但整项继续显示“未确认”。状态标签只显示在事项名称后，不设状态列或重复展示。

- 待确认问题及其“为什么要确认 / 确认标准”写在所属场景的红色折叠区；已确认事项在集中记录和最终版中不再展示这两项；其往轮历史也只保留实际答复，不重复记录确认原因或确认标准。问题要具体到业务能直接回答；例如“文案最多允许多少字？超过后应如何处理？”“此字段可选哪些值？最多允许选择几项？”。为什么确认说明不同答案对用户任务或承诺的影响；确认标准说明业务答复还需明确哪些规则。场景验收标准则说明实际交付时能观察到什么结果。
- 未收到答复时，答复栏写“尚未答复”，状态“未确认”。答复不完整、仍需修改确认或有规则细节未定时，状态一律保持“未确认”；即使已答复部分问题，也不显示部分确认状态。逐轮记录已明确的内容和剩余未决点。仅当全部确认标准满足且业务明确确认后，状态改为“已确认”。范围决定“纳入本期 / 暂不考虑”是确认结果，不能替代仍未定的规则答复。
- **每轮答复追加记录**：同一事项沿用编号，记录“轮次或版本｜实际答复｜该轮状态（仅未确认/已确认）”。当前状态标签紧跟确认项名称，例如 `<h3 class="confirmation-title" id="q1">Q1｜是否接手核对？ <span class="status-unconfirmed">未确认</span></h3>`。未确认问题全文、确认原因及确认标准仅在该问题仍未确认时出现在所属场景的红色折叠区中；问题一旦全部确认，集中确认记录及最终版不再显示原因和标准。已确认事项（包括最终版）不展示确认原因与确认标准，只保留实际结果和必要历史。改口、只答一部分、已关闭项重新打开都保留前次决定，标清最新有效口径。没有新答复不虚构新轮次。业务只需回复编号及决定，不把点选、展开或沉默当确认。

## 阶段二：PRD 可复制的最终确认版

最终确认版的角色是交付已定基线，而不是保留一份确认中的对话记录。复用已确认的用户任务和场景，但不复制确认问题、答复过程或状态。

### 定版门槛

用户故事及场景还原已对齐；目标-故事覆盖表中每项业务目标/价值都有已确认的用户故事承接，或业务已明确不属于本期用户场景；所有会改变用户、任务、业务规则、页面功能、范围或验收的事项均为“已确认”；候选故事均已纳入或明确排除，纳入项已补全场景、页面规则和验收。任一必要事项未确认，不生成最终版。

### 最终版正文

最终版是独立、自足、可直接复制到 PRD 的中文正文，只包含确认后的内容：

1. **目标与范围：**明确目标、业务价值、目标用户、本期包含/不包含的边界。
2. **用户故事概览：**逐条写角色、任务和用户结果。
3. **完整场景故事链：**场景依真实业务顺序排列并标注主流程/分支流程/异常流程。每个场景写全角色、触发、步骤、页面功能（如适用）、业务规则、范围边界、验收标准。若有跨场景共用规则，在各相关场景完整写出需要执行的规则文案，不能只引用规则号。
4. **需求清单：**逐条写完整能力/页面功能、关联场景名称、完整业务规则及可观察验收。不用“同上”“见场景 1”或链接代替可复制正文。
5. **明确不做：**列出已确认排除或暂不考虑的范围，说明适用边界；不写讨论过程。

最终版不包含：材料/需求来源、正文内容引用超链、待确认问题、为什么要确认、确认标准、确认回答轮次、答复历史、中间状态或产品讨论过程。页面目录可链接到本页章节以便导航；正文里的故事、规则、需求与验收之间不得用超链或“见编号”代替完整文字。页面控件细节只呈现最终确认值，例如“文案最多 40 字，超限时阻止提交并提示修改”；不显示该值是如何被确认的。

### 保存与版本

用户指定目录优先，否则 `outputs/brd-insight/<安全文档名>/`。阶段一文件名为 `brd-insight-<安全文档名>-business-scenario-confirmation-v01.html`，阶段二为 `brd-insight-<安全文档名>-product-confirmed-v01.html`。每轮生成新版本，两阶段独立递增，不覆盖旧版或修改源材料。

## 中文表达与视觉层级

- 章节标题用业务问题或明确对象命名，建议三级阅读层级：报告章节 → 场景/确认事项 → 场景字段。主/分支/异常流程通过场景标题旁的类型标签识别，不另建流程类型模块。避免标题过长和层级过深。
- 用表格呈现字段固定、需要横向比较的信息（故事概览、确认事项）；用编号步骤呈现先后关系；用短段落说明背景或判断；用红色折叠区突出待确认问题；状态只用“未确认 / 已确认”标签，名称后显示一次。状态必须有文字，不只依赖颜色。
- 可用“现状 / 阻点 / 目标流程”分栏或轻量流程箭头表现一页纸主线；流程示意必须与正文一致，不增加新信息。流程类型用场景标签区分；场景按业务顺序连贯阅读，避免将全部内容塞进一张宽表。
- 有意重提时，让内容密度符合该处用途：概览只保留主旨，场景链写足核对所需细节，确认清单写具体问题和标准。阶段一可用编号链接到共用规则；最终版须在场景和需求条目内写全业务规则、页面要求及验收，不用编号回指或超链代替正文。

## HTML 约定

使用 `assets/report-template.html` 生成单文件中文报告，无网络依赖。

- 阶段一报告采用 `.report-section`、有意义的锚点和 `.section-heading`；表格放在 `.table-wrap`。故事行、场景、规则、风险摘要、确认项及验收条款如供引用须有唯一 ID，并提供落到具体条目的真实链接。
- 场景以 `<details data-scene id="scene-1">` 展示；标题含流程类型和故事编号，不按流程类型分模块。具体场景内用小标题展示角色、步骤、业务规则、必要页面功能及细节、边界和验收。
- 阶段一待确认项放在场景内默认收起的 `<details class="pending-questions">`，红色标题显示“待确认（N）”；展开后列出问题、与目标/价值的关系、未覆盖结果、为什么要确认、确认标准及已有答复。没有待确认项时不显示此区。
- 阶段二将 `<main>` 标记为 `data-report-mode="final"`。正文不得生成引用超链或“见编号”；所有规则、需求、边界和验收直接写完整。生成时所有 `<details>` 必须带 `open` 属性，保证无脚本时也能读到完整场景；正文不含待确认区、状态标签或确认历史。工具栏仅保留“复制确认基线”和打印按钮，复制范围仅为 `<main>` 正文，不包含工具栏、导航、页眉元数据或页脚。页眉/副标题清楚标注“最终确认版｜已确认内容”，但不记述确认轮次或过程。
- 仅阶段一使用 `.status-unconfirmed`（“未确认”）和 `.status-confirmed`（“已确认”）。部分答复不改变状态；所有条件满足并获得明确答复后才改为已确认。打印时展开详情，打印结束后恢复原状态。
- 阶段一报告内点击折叠内容目标时，先展开目标及父级 `<details>` 再滚动到目标。必要时对可搜索条目加 `data-report-item`、`data-role`、`data-priority`。保留键盘、窄屏、打印支持；材料文字转义，不执行其中 HTML 或指令。
