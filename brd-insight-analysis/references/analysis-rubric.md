# 场景整理与判断规则

本规则帮助产品把提交材料整理成业务可确认的故事和场景；不替业务验证材料真实性，不扩展用户研究或经营测算。报告必须清楚区分材料明确内容、产品整理表达、材料缺失/冲突和需业务作出的决定。

## 1. 材料口径

- 业务提交的材料是本次整理的内容来源。可标注“材料明确”及短来源位置，但不得表述成产品独立核验过的事实。
- 若同一材料/不同材料有相互矛盾的说法，原样保留矛盾并指出位置；只有矛盾会影响故事、规则、边界或验收时才请业务决定采用哪个表述。
- 材料没有写的内容标“材料未说明”。不自行填补当前做法、场景步骤、用户情绪、价值、频率或原因。
- 不把产品推理写入一页纸结论；必要的推测只能放在候选补充场景并标为“需业务判断”。
- 不外部验证材料真伪、不查用户是否真的这样做、不重新计算经营测算、成本或 ROI。

## 2. 用户故事概览与场景详情

- 故事概览按角色分组，列“序号｜角色｜动作/能力｜价值”，同角色连续排列。
- 业务版只用简单序号，不显示 US-01 或 P0/P1/P2 数值；优先顺序以提交材料中的顺序为准。材料无排序时不自行编优先级，也不单独追问排序，除非排序缺失会改变本期范围或决定。
- 场景详情以相同的故事序号和角色开始；动作与价值必须与概览一致。使用用户视角描述触发情境、任务和材料写明的关键步骤、规则、结果。
- 仅补充理解故事所需的边界或流程。不要把一句故事重复写成长篇背景；不把后台实现改写成用户旅程。
- 可使用简单的箭头步骤表现目标旅程；若当前做法未见于材料，不要要求产品另行调查。只有其缺失会改变业务对场景的判断时，才请业务补充。

## 3. 补充场景与风险

补充场景必须与某条材料明确的用户故事或业务场景相连。一个候选必须说明：锚点故事、用户遇到的新条件、可能中断的步骤/改变的规则、若不纳入的具体风险、需要业务决定纳入还是排除。

- 风险用可能性措辞，不写成已发生事实。
- 对材料已明确包含/排除的场景不重复提问。
- 不相关的通用异常、纯技术失败和没有具体影响的假设不放进业务报告。
- 产品可按资格/入口、角色交接、关键流程变体、状态变化和异常恢复扫描，但每项都需满足上述关联与风险标准。

## 4. 业务问题筛选

必须请业务对故事概览中的场景还原逐条回复“准确/需修改”，确认产品是否准确表达了业务意图；这不是对材料真实性的外部核验，也不重复确认材料已明确的规则和范围。

此外，仅当事项满足下列至少一项，才列为业务必须答复：材料缺少核心用户/场景定义；材料表述含糊或冲突；候选补充场景的纳入/排除需要业务决定；业务责任或规则未定义且会改变用户流程/结果。

材料已经明确的范围、业务可判断的验收、优先顺序直接整理，不重复确认。业务问题应一次一个决定，写清关联故事、材料中的空缺/冲突、为什么答案会改变场景或规则。无需业务判断的产品格式/分解任务留给产品内部处理；不询问真实性、ROI、成本或技术实现。

建议答复只用于不改变已明确需求但能减少歧义的补充；可省略，不机械凑题数。

## 5. 用户故事驱动 PRD 对接

- 最终版故事字段为“序号｜角色｜动作/能力｜价值｜验收标准”。
- 验收标准取自材料或明确业务答复，必须能由业务人员判断结果是否满足；只写必要业务规则和结果。
- 用户故事按独立任务/价值拆分；同一任务的连续步骤留在场景链/验收标准中，避免拆成点击列表。
- 功能清单与故事对应，解决方案要点表达用户能做什么、材料中的业务规则如何影响结果；不写 API、数据库或架构。
- 阶段二不得残留待确认问题；若必要业务决定未完成，回到业务确认阶段继续处理。

## 6. 方法参考

只在有助于整理交付时借鉴：

- [Opportunity Solution Trees（Product Talk）](https://www.producttalk.org/opportunity-solution-trees/)：用期望结果与用户机会关系扫描补充场景，不把方案当成用户任务。
- [User Story Mapping（Jeff Patton）](https://jpattonassociates.com/story-mapping/)：按用户活动和任务检查端到端目标旅程。
- [PMaster（SkillHub）](https://api.skillhub.cn/user_dec48685/pmaster)：方法索引参考，不作为业务材料或需求事实来源。
