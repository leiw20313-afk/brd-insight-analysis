# 从业务材料到确认稿

1. **拆清现状与目标。**先找首期用户、现行做法和实际阻点；再找业务提出的流程、范围和预期结果。只有功能名称而没有用户事件时，不反推购买原因或真实经历。用[首期用户判断](user-synthesis.md)辅助分析；汽车模板只作[字段定位](brd-template-map.md)。内部可回查依据，对外不展示出处。
2. **从目标价值推导故事覆盖。**把每项目标/价值转为用户应得到的结果，检查是否有目标用户、触发情境、任务和必要步骤支撑；再检查达成该结果所需的角色交接、关键分支、状态变化和失败恢复。每个目标/价值必须有明确去向：由已确认故事承接、提出有目标锚点的待业务确认候选，或由业务明确说明不属于本期用户场景。提出候选时写明未覆盖的用户结果及若不纳入的具体风险，不得将推导写成既定事实；覆盖检查旨在系统发现缺口，不宣称穷尽现实中的所有情境。
3. **从任务到路径。**每项独立任务生成一行故事概览；用相同编号把故事连到按发生顺序排列的场景；每个场景只加主流程、分支流程、异常流程等类型标签，不按类型拆模块。只写改变结果的交接、条件和边界。概览、结论与场景详情可以因阅读目的适度重提核心内容，不强制把场景限定在单一位置。场景详情按[统一字段](report-contract.md)组织，让业务能指出“角色不对”“漏了这一步”或“这个结果不该承诺”。
4. **按场景识别页面规则。**逐个场景判断用户是否需要产品页面能力来完成录入、选择、查看、编辑或提交。若需要，在场景里写清业务可见的页面能力，并将影响任务的细节列为待确认问题，例如自由文案的字数上限和超限处理、枚举字段的可选值及选择数量上限、必填性与校验反馈。只问当前场景实际需要的规则；不编造限制值，也不向业务确认 API、布局实现等技术方案。每个未确认规则需写业务回答会影响哪条故事规则或验收。
5. **区分遗漏与既定分支。**沿已明确故事扫描资格、角色交接、状态变化和失败恢复。材料已明确的异常直接放在对应场景位置并标“异常流程”；新想到且有具体影响的，另列为“风险遗漏场景”，先写若不考虑的风险，再写场景详情。处理方式尚无决定时，描述可能断点，不替业务指定解决方案。
6. **设计能得到决定的问题。**一问处理一个分歧，给出实际条件、动作及其后果；明确答复需要覆盖哪些点。内部可判断应找谁协助，对外统一按未决程度和故事顺序展示，不做角色分栏。已明确的事实、优先级、规则不重复提问。每项未确认问题及其原因、确认标准直接放在所属场景的红色折叠区。
7. **处理下一轮。**按编号将答复与确认标准对照。只用“未确认 / 已确认”两种状态；部分答复可记入结果，但只要仍有细节未定，整项保持“未确认”。所有内容均明确且得到确认后才标“已确认”。追加该轮实际答复和状态，同步场景规则/页面功能、范围和验收；阶段一报告内链接更新并校验。已确认事项与最终版不展示确认原因和标准。最终版改为完整自足正文：展开全部必要场景，不保留问题状态、答复历史或内容引用链接。不可用“已沟通”“已处理”替代实际答复。
