# 汽车业务需求洞察

让业务判断：**产品还原的是不是我的原意？哪些边界还没定？** 先理解首期用户和影响购买或采用的需求，再确定本期承诺。不是 BRD 写作评审，也不代写 PRD。

## 阶段一｜场景确认稿

按[分析路径](references/analysis-playbook.md)整理，按[报告契约](references/report-contract.md)输出中文离线网页。阶段一依次呈现：

1. **一页纸结论**：用业务语言写明目标用户与任务、现在怎么做、哪里受阻、流程一句话、本期范围及确认进度。区分现行做法与目标流程；不把设想写成事实。
2. **用户故事概览**：先从业务目标与价值逐项推导目标用户要取得的结果，再检查谁在什么情境下需要完成什么任务。每项独立任务一行，列序号、角色、用户要做什么、得到什么结果；序号链接到对应场景。
3. **场景故事链**：按真实业务发生顺序排列场景；每个具体场景单独标注“主流程 / 分支流程 / 异常流程”等类型，不按类型拆成模块。根据业务目标与价值检查用户、触发情境、主任务、必要分支、角色交接及失败恢复，提出所有有明确目标/价值锚点的缺失场景故事，供业务确认；候选场景须标明关联目标/价值和未覆盖的用户结果，不得把推导写成已发生事实。角色、步骤、业务规则、范围边界和验收标准放在各自场景下。结合具体场景检查是否需要页面字段、输入/选择/展示能力；如需要，明确会影响用户规则的文案限制、枚举范围/数量、必填性及校验结果，并交业务确认，不自行补定数值。待确认问题须说明关联的目标/价值或场景，以及未明确的页面规则。场景内的待确认内容以醒目的红色提示，默认收起，展开后可直接查看问题、为什么要确认、确认标准和已有答复，并在原场景内回复，无须跳转。
4. **风险遗漏场景**：锚定已明确故事，先说明“若不考虑”的具体风险，再列场景步骤、规则和边界；明确请业务决定“纳入本期 / 暂不考虑”。未决定前，不混入已承诺流程。
5. **确认记录**：待确认问题全文、确认原因和确认标准放在所属场景的红色折叠区。确认记录只保留确认项名称、当前状态标签、实际答复和历史答复。已确认事项的历史也不重复展示确认原因或确认标准。状态只有“未确认 / 已确认”：答复不完整或还有任何细节未定，一律“未确认”；全部确认标准均满足并明确答复后才为“已确认”，不设部分确认、需修改或待复核状态。

## 阶段二｜最终确认版

只有故事还原已对齐、必要决定均已确认、风险遗漏场景已取舍且纳入项已补齐规则和验收，才形成 PRD 输入基线。最终版标题清楚标为“最终确认版｜已确认内容”，是可直接复制到 PRD 的独立正文：只呈现已确认的目标、用户故事、完整场景、页面功能与业务规则、范围边界、需求和验收；不带内容引用超链，不展示确认问题、确认原因/标准、答复过程或历史记录。所有必要描述直接写全，不用“见故事/规则/验收编号”替代正文。详见[定版门槛](references/report-contract.md#定版门槛)。

## 文案与页面

- 全文使用简洁、专业的中文，业务术语前后一致；优先沿用业务常用说法，首次出现的必要专业术语用短句解释。概览回答“有哪些任务”，详情回答“实际上怎么走”，结论可摘要关键事实，确认清单可引用相关场景。**不强制同一场景只完整呈现一次**；因阅读目的不同可适度重复，保持编号、术语、状态与结论一致，避免机械复制或冗余铺陈。
- 阶段一不展示材料出处，但报告内交叉引用需可点击直达。阶段二不显示内容引用超链，规则、步骤、边界、功能和验收写成可独立复制的完整文案。内部区分材料事实、业务答复与产品推导；不补造现行流程、动因、规则、阈值或确认答复。材料只有提案时标“目标场景”。不外部核验材料或 ROI。
- 使用[HTML 模板](assets/report-template.html)。通过分层标题、简明表格、编号步骤、流程箭头和状态标签增强可视化；表格服务于对照，步骤服务于顺序，避免装饰性图表和信息堆叠。搜索、筛选、展开/收起及打印保留。页面操作不是答复，不改变确认结果。
