# 汽车业务需求洞察

将业务提交的 BRD、会议纪要等材料，整理成业务人员容易看懂、便于确认和补充的**用户故事与真实使用场景**。目标是减少需求误读、场景漏项和未经确认的推断。

## 两阶段流程

### 阶段一｜业务场景确认

面向业务负责人。报告围绕“材料已明确的用户和场景是什么、用户如何完成任务、还存在哪些与本期场景相关的遗漏、业务需要回答什么”展开；不是 BRD 文档评审。

**按 [分析作战路径](references/analysis-playbook.md) 和 [报告契约](references/report-contract.md) 输出：**

1. 一页纸结论只写输入材料明确写出或业务此前明确确认的内容；需业务回答的事项另列，不混入结论。
2. 用户故事概览按角色分组，以“序号｜角色｜动作/能力｜价值”展示。
3. 场景故事链以用户视角展开，与同序号用户故事一一呼应；话少但准，保留理解用户任务和边界所必需的信息。
4. 补充材料未提出、但与已确认场景有关系且不考虑可能有风险的场景，请业务决定是否纳入。
5. 需业务回答的问题单独展示：业务逐条确认故事/场景还原是否符合预期；对材料缺失、含糊或冲突且影响场景决定的事项再提问。材料已经明确的范围、验收结果和优先级直接引用，不重复追问。

不展示“材料清单”“用户画像/角色盘点”“种子用户候选”“真实动因/问题链”等独立模块。角色只在用户故事和对应场景中出现。不得要求产品另行验证业务材料是否真实，也不检查经营测算或 ROI 口径；按提交材料整理，若材料内部冲突或关键含义不明，只就影响场景理解/范围的具体冲突提问。

### 阶段二｜产品最终确认版

只有业务对需答事项和相关补充场景作出决定后，整理成可直接用于 PRD 编写的确认基线。用户故事表为“序号｜角色｜动作/能力｜价值｜验收标准”；功能清单需逐项写解决方案要点、对应故事和验收结果，并按“关键／重要／一般”分组。执行 [报告契约](references/report-contract.md) 的最终版要求。

### 页面与交互

两阶段均输出单一离线 HTML，使用 `assets/report-template.html`。页面支持章节跳转、搜索、按角色/功能优先级筛选、长内容展开/收起、打印/另存 PDF 和返回顶部；兼顾键盘、读屏、窄屏和打印。交互只改善阅读，不改变场景结论，不将点击状态当成业务答复。

## 全程规则

- 业务提交材料是本次分析的事实来源；如实归属来源，不额外联网核验业务描述，不推测材料之外的用户事实。
- 材料中明确的范围、验收结果、优先级直接整理进报告，不重复列为待确认。只有缺失、含糊、冲突且会影响场景或业务决定的内容，才形成业务问题。
- 一页纸结论只放材料明确/业务已确认的内容；分析、候选补充场景和待答问题分区展示。
- 故事和场景用业务日常语言，删除重复赘述。详情必须回应同一故事序号的角色、触发情境、用户任务、材料所述做法/流程、结果与必要边界；材料未写的关键步骤标“材料未说明”，不补造。每条故事须单独留出业务回复“准确/需修改”的位置。
- 用户故事概览不显示 US 编号或 P0/P1/P2 数值；同角色连续排列，只按材料中的优先顺序展示。
- 候选补充场景必须锚定一个已确认/材料明确的故事，写清如果不考虑的具体风险，供业务决定是否纳入。
- 不展示种子用户、购买动因或外部真实性验证模块；不核验经营测算、成本口径或 ROI。
- 不把产品内部整理工作、技术实现问题或对业务材料真实性的质疑包装成业务问题。
- 阶段二最终版不含待确认问题；各阶段版本独立递增，保留历史，不覆盖旧报告或修改源材料。具体保存规则见 [报告契约](references/report-contract.md)。
